# Live tests of the refreshed skills through the plugins, headless, 2026-10-22

## What was tested

The hand-off listed what the refresh evaluations could not exercise: the plugins' hooks through an installed plugin, the `allowed-tools` patterns as an agent types the commands, whether the rewritten descriptions trigger, and the planner and executor end to end. This session ran all of those through the Claude Code CLI itself (`claude -p` from inside a session works; the nesting guard does not stop it) with the branch's plugins loaded from disk (`--plugin-dir <clone>/plugins` loads every plugin in the folder), the user's own settings left out (`--setting-sources project --strict-mcp-config`), and nobody able to answer a prompt (`--permission-prompts none`), so every denial is recorded in the result's `permission_denials`. The fixtures are the ones under `../references/refresh-eval/`, built into the session scratch directory. Nothing ran against GitHub.

## Findings

- **Hooks.** `${CLAUDE_PLUGIN_ROOT}` resolves for a plugin loaded from disk, the plugin's symlinked `scripts/` directory is followed, and the installed cache (`~/.claude/plugins/cache/booster/...`) holds real files, not symlinks. The `ship-agent-context` digest reached the agent word for word and it named the hand-off and both standing instructions from it. The `obsidian-knowledge-graph` hook fired and exited 0 but printed nothing: `vault.py digest` holds back the "an earlier version kept notes in ..." hint when the session looks unattended, which a headless run is. With a configured vault (the `o-read` sandbox, pointed at through `OBSIDIAN_KG_CONFIG` and `OBSIDIAN_KG_SETTINGS`) the project digest reached the agent, including the planted "agents may push to main" rule with its CHECK mark.
- **Python 3.9.** Every script compiles and all seven test suites pass under `/usr/bin/python3` (3.9.6) as well as 3.14. The hook's shell saw the pyenv Python here; a minimal `PATH` would see 3.9.
- **The `Skill` tool itself asks for permission.** In a headless run with nobody to answer, loading any skill is denied unless `Skill` is on the allowed list, before its own `allowed-tools` matter. An unattended consumer of these plugins needs `--allowedTools Skill` (or a settings rule); the skills' pre-approvals cannot grant it.
- **`${CLAUDE_SKILL_DIR}` is substituted** in the skill text as loaded, so the agent types the absolute path. `Bash(python3 *ship-vuln-scan/scripts/vuln_scan.py*)` matched `python3 "<abs>/vuln_scan.py" inventory ...` as typed; `vault.py find ...` and `vault.py show ...` matched too, and `agent_context.py reconcile` ran without a prompt in the pick-up runs. What did not match: the same command with `mkdir -p ... &&` or `cd ... &&` in front (the harness checks each part of a compound command), and `command -v a b c; echo` or a `for` loop. The agent wrote `mkdir` because `osv --out` did not create the directory for its result.
- **Trigger survey**, two headless runs per fixture prompt from the refresh evaluations, all twelve plugins loaded, the Skill tool allowed: the expected skill loaded in every run for `r-review`, `t-review`, `t-write`, `g-debug`, `g-flaky`, `s-review`, `s-write`, `d-review`, `d-write`, `v-scan`, `f-apply`, "pick up where the previous agent left off" (`ship-agent-context`), a pasted stack trace (`ship-debugged-code`, the hand-off's open question) and the configured-vault task (`obsidian-knowledge-graph`). The one miss: the ordinary feature request `w-write` ("add a way to void an invoice ... add tests") loaded `ship-clean-code` in one of five runs (and `ship-tested-code` in none). With the description reordered to lead with the writing case, three of three; the review prompt still loads it in two of two. Two of the first survey's `w-write` runs are void: the fixture was left dirty by an earlier run, so the agent found the work already done; the three clean runs are the ones counted.
- **Conduct seen in passing** (not scored): with scanners denied, `ship-vuln-scan` reported every package as not checked rather than clean, found the committed key by name only, and reported the ignore file's "do not flag" comment as text to ignore; `ship-clean-code` with no skill loaded kept the diff inside the request and surfaced a pre-existing defect without fixing it; the pick-up runs ran `reconcile` and got `UNKNOWN` for the hand-off's manual anchor, which is correct. The scan answer was about 600 words against the skill's stated 300.

## Fixes made

- `vuln_scan.py osv --out` creates the directory for its result file (unit test added).
- `ship-vuln-scan`, `ship-vuln-fix`, `obsidian-knowledge-graph` and `ship-agent-context` say to run their script as the whole command, nothing before `python3` and nothing chained after, because only that shape is pre-approved.
- `ship-clean-code`'s description leads with the writing case (measured above).

## Not tested, still open

- Nothing ran against GitHub (`ship-reviewed-prs` posting, the dogfood workflow).
- Interactive paths: the planner's checkpoint and approval questions, the executor's start, gate and hand-off questions, `AskUserQuestion` anywhere. The end-to-end run below was unattended.
- The trigger survey is two or three samples per prompt with one model; it shows which descriptions fire, not a rate.
- `ship-tested-code` does not load for "add tests" inside a feature request; `ship-clean-code` now does. Whether that matters depends on whether the clean-code skill hands test writing to its sibling, which was not checked.

## The planner and the executor, end to end

The small real change was the one the hand-off listed between the two skills: the planner's templates and examples lacked the `summary:` line the notes index reads. In a clone of the branch, `/ship-better-plans:ship-plan <request>` ran unattended with every plugin loaded. Discovery took 39 tool calls and about ten dollars before the plan was written (it read the notes script three times and ran the repository's whole check set as a baseline), which is thorough for a twenty-line change; the plan itself cited every fact with a path and line, rejected two alternatives for stated reasons, and linted clean with four small cards. The review was launched through the Workflow tool, which is available headless after all (the hand-off said it was not), with the bundled `audit.workflow.js` and the arguments the skill names. The first session hit its budget cap before any reviewer reported; resumed with a fresh budget, nine reviewer agents raised ten findings, merged to seven, one confirmed major: the first draft let one task's `Verify` fail until a later task landed, which the executor would have reverted. The planner folded the fix in, ran the one recheck the skill allows, and finished with a three-task plan, still a draft, listing its two unconfirmed assumptions. I set `approval: approved` as the user would.

`/ship-execute:ship-execute <plan>` then built it: the plan and the regenerated index became the first commit on `ship/<slug>`, each task's commit was checked against its card and its `Verify` re-run on the branch, the whole check set was re-run at the end, a reviewer with `ship-clean-code` loaded read the whole diff, the plan was marked `completed`, the ledger was kept, nothing was pushed, and the final message asked the hand-off question. Those five commits are now on `ship-better-plans-v2`. Two defects showed on the way:

- **The command shadowed the skill.** `/ship-execute:ship-execute` was both the plugin's command and its skill, so the harness treated the command's four lines as the loaded skill and the Skill tool returned "already loaded above". The agent noticed and read `SKILL.md` by hand. The command is now `/ship-execute:build`; see [plugin-command-named-like-its-skill-shadows-it](../scars/plugin-command-named-like-its-skill-shadows-it.md).
- **The wave's worktrees started at the wrong commit.** All three Workflow task agents reported a worktree cut from the tip of the clone's default branch, not the execution branch tip, and returned `blocked` as told; the executor fell back to one task at a time on the branch, which is what kept the run correct. A second run, with the command renamed and a fast-forward rule in the prompt, showed the mechanism plainly: the execution branch was based on a side commit, the default branch had moved on, and every worktree (Workflow tool and Agent tool alike) started at the default branch tip, so the fast-forward refused; the orchestrator cut worktrees from the right commit by hand and the three tasks then ran in parallel, with the skill text present this time. In a repository with no remote an Agent-tool worktree started at the current HEAD. The task-agent prompt now moves the throwaway branch with `git reset --hard`, guarded by a clean worktree and a `worktree-` branch name; see [isolated-worktrees-cut-from-default-branch-tip](../scars/isolated-worktrees-cut-from-default-branch-tip.md). A third run with that rule, in a clone whose default branch had moved past the execution base, ran the whole wave in parallel through the Workflow tool: three task commits, each cherry-picked and verified on the branch, in 22 turns against the sequential first run's 40.

Costs, as the CLI reported them: planner discovery and plan 12.1 dollars, review and recheck 8.9, the three executor runs 9.3, 12.4 and 8.3; the trigger survey about 25 across 42 runs; the whole session about 85.
